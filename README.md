# Hackathon Harness — 사용법 (3시간)

주최 측 프로젝트의 `README.md`와 코드를 **덮어쓰지 않는** Codex 보조 하네스입니다. 문제별 정답 코드는 포함하지 않습니다. 개인 GitHub 코드 반입이 허용되는지 먼저 확인하세요.

**보안:** `git push` 및 다른 원격 업로드/게시 명령은 금지합니다. 하네스에는 `config/` 폴더가 없으며 180분 시간표는 이 README에만 유지합니다.

## 1. 설치 (주최 측 프로젝트 루트에서)
```bash
git clone <내_저장소_URL> .hackathon-harness
python3 .hackathon-harness/scripts/preflight.py
```

## 2. Codex 첫 메시지 (복사해서 사용)
> 주최 측 루트 README.md 및 제공 파일을 먼저 읽어줘. `.hackathon-harness/AGENTS.md`와 필요한 `.hackathon-harness/.agents/skills/*/SKILL.md`를 읽고, 담당자에게 확인할 핵심 질문(최대 5개, 선택지·영향 포함)을 먼저 `.hackathon-harness/workspace/`에 기록해줘. 질문을 출력한 뒤 멈춰. 내가 담당자에게 직접 물어보고 답을 전달하면 요구사항과 설계 대안을 정리해줘. P0 미확정 상태에서는 설계·구현하지 마. 설계 승인 전에는 구현하지 마. 주최 측 README.md를 수정하지 마.

## 3. 진행
- **0–15분:** 요구사항·모호점·담당자 질문 및 답변 반영 (응답 지연 시 시간표 조정)
- **15–40분:** 알고리즘 대안·설계 승인
- **40–105분:** 최소 동작 버전 구현
- **105–140분:** 실제 실행·테스트·결함 수정
- **140–165분:** 측정 기반 최적화 (필요한 경우)
- **165–180분:** 최종 검증·설명·제출

## 4. 검증
실제 프로젝트의 테스트 명령으로 바꿔 실행하세요. 아래는 Python 프로젝트 예시입니다.
```bash
python3 .hackathon-harness/scripts/verify.py --project . --command python3 -m unittest discover
python3 .hackathon-harness/scripts/collect_evidence.py
```

**경로:** 코드는 주최 측 프로젝트에 작성하고, 분석/결정/테스트 기록은 `.hackathon-harness/workspace/`에 작성합니다. `verify.py`는 지정된 명령만 실행하며 자동으로 프로젝트를 탐색하거나 안전성을 보장하지 않습니다. `collect_evidence.py`는 기록 파일의 목록과 해시만 만듭니다. 테스트 통과 증명은 `verify.py` 로그를 확인하세요.

## 5. 서술형 문제 대비 (구현 후, 최종 10분 권장)
```bash
python3 .hackathon-harness/scripts/prepare_written.py --project .
```
이 명령은 주최 측 코드를 변경하지 않고 `.hackathon-harness/workspace/`에 소스 목록과 다음 두 문서를 준비합니다.
- `PROJECT_EXPLANATION.md`: 문제·목표·설계·알고리즘·검증·한계·예상 서술형 답변
- `IMPLEMENTATION_DETAILS.md`: 파일별 역할·함수·실행 흐름·코드 근거

**Codex 후속 요청:** “실제 구현 코드와 실행한 테스트 로그를 읽고 두 문서를 구체적으로 채워줘. 각 설명에 파일/함수 근거를 적고, 미검증 사항은 명시해. 서술형 답변 6개를 짧게 작성해줘.”

생성 스크립트는 소스 파일 목록만 자동 추출하며 **코드 해설은 Codex가 실제 코드를 읽고 작성**해야 합니다. 기존 두 문서가 있으면 덮어쓰지 않습니다.

## 담당자 실시간 질의 (설계 전 필수 게이트)
1. Codex가 `workspace/QUESTIONS.md`에 P0/P1/P2 질문 최대 5개를 정리하고 **대기**합니다.
2. **사용자가 직접 담당자와 협의**한 뒤 답변을 Codex에 전달합니다.
3. Codex는 질문과 전달받은 답변을 기록합니다. 실제 영향이 있을 때만 요구사항을 갱신합니다.
4. P0가 해결되면 설계안을 제시하고 사용자 승인을 받습니다. P1/P2 미확정 사항은 사용자 승인하에 가정으로만 진행합니다.

**답변 전달 프롬프트:** “담당자 확인 결과: Q01=..., Q02=... . QUESTIONS.md에는 질의응답만 기록해줘. 요구사항 분석과 설계 시 참고하되, 답변을 자동으로 요구사항이나 설계 결정으로 확정하지 마. 중요한 미해결 P0는 알려줘.”


## 설계 기록 원칙
- `workspace/QUESTIONS.md`: 담당자 질문과 답변만 간단히 기록합니다.
- `workspace/DECISIONS.md`: 알고리즘·설계 선택 이유와 대안, 코드·테스트 근거를 기록합니다.
- 담당자 답변이 설계 선택에 실제로 영향을 준 경우에만 Q-ID를 연결합니다. 연결을 강제하지 않습니다.
- 평가 대응의 우선순위는 요구사항 충족, AI 활용 과정의 주도성, 설계 이해, 실제 실행·검증 증거입니다. 긴 문서 작성보다 동작하는 코드와 확인 가능한 결과를 우선합니다.

## QUESTIONS.md 활용 규칙
- **기록:** 질문과 실제 답변만 간결하게 보관합니다.
- **요구사항 분석:** README를 우선하고, 질의응답은 해석을 돕는 참고 자료로 읽습니다.
- **설계:** 기술적 근거와 대안을 별도로 비교합니다. 답변이 실제 결정에 영향을 준 경우에만 Q-ID를 인용합니다.
- **성능 최적화:** 답변에 포함된 제약·평가 의도를 참고하되, 동일 조건의 전후 측정과 회귀 테스트로 개선을 판단합니다.


## 6. 짧은 자연어 명령 (Codex)
**처음 한 번** Codex에 다음을 입력하세요 (하네스 폴더의 `AGENTS.md`는 주최 측 프로젝트에 자동 적용되지 않을 수 있습니다).

> `.hackathon-harness/AGENTS.md`를 읽고, 이 대화에서 아래 6개 짧은 명령을 해당 워크플로로 실행해줘. 주최 측 README.md는 수정하지 마.

| 입력 | 수행 작업 |
|---|---|
| `문제 분석해줘` | 명세 분석, 요구사항 정리, 담당자 질문 기록 |
| `설계해줘` | 알고리즘 대안 비교, 설계안 제시, **승인 대기** |
| `구현해줘` | 승인된 설계로 최소 동작 코드 구현 |
| `검증해줘` | 실제 테스트 실행, 결과 기록, 실패 수정·재검증 |
| `최적화해줘` | 병목 측정, 개선 전후 비교, 회귀 검증 |
| `서술형 준비해줘` | 소스 분석 및 설명 문서 2개 완성, 예상 질문 6개 |

질의응답은 `QUESTIONS.md`에 단순 기록하고 분석·설계·최적화 때 참고만 합니다. 명세와 다른 임의 해석을 확정하지 않습니다. `검증해줘`는 실제 실행 가능한 환경과 권한이 있어야 하며, `서술형 준비해줘`는 코드 해설까지 작성해야 완료입니다.

TDD 프롬프트 (설계 다음 구현시에 사용)
승인된 설계를 경량 TDD 방식으로 구현해줘. 핵심 요구사항별 테스트를 먼저 작성하고 실제 실패를 확인한 뒤, 최소 구현으로 통과시켜줘. RED-GREEN-REFACTOR를 작은 단위로 반복하고, 기존 테스트와 통합 테스트를 계속 실행해줘. 테스트 환경 구축에 시간이 과도하게 걸리면 간단한 검증으로 대체하고 이유를 기록해줘. 과설계를 피하고 실행 가능한 MVP를 우선 완성해줘. 테스트 실행 결과와 구현 근거를 기록하고, git push 및 원격 업로드는 절대 하지 마.
